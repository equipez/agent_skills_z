# Maintaining the shared writing skill

Use actual revision experience to improve this workflow. Keep the nine proof
rules intact unless the requested change explicitly concerns those rules.

1. Identify the passage, intended reader, feedback, and underlying writing
   problem. Distinguish a general principle from a project-specific notation
   convention or a correction to the mathematics.
2. Refine the narrowest relevant rule. Retain the conditions under which the
   advice helps and remove conflicting duplicate guidance.
3. Add an example when it clarifies a judgment that the rule alone does not
   settle. Give enough setting and a target for the example to stand alone.
   Before/after versions should preserve the mathematical claims; disclose
   separately any mathematical correction.
4. Check nearby rules for unwanted interactions. For example, concision must
   not remove a necessary intermediate relation, and matrix notation must not
   hide a genuinely componentwise argument.
5. Validate relative links, metadata, helper behavior when changed, and the
   standalone archive. For substantial instruction changes, use realistic
   writing tasks and inspect the resulting passages for preserved assumptions
   and evidence limits. A metadata validator alone cannot assess writing quality.

Keep the main instructions concise and put detailed cases in references.
After experience on one or two papers, consolidate stable principles instead
of accumulating a separate command for every rejected phrase. Manuscript
editing and installation remain within the user's requested scope. Sharing
this skill does not authorize contacting an author, publishing a manuscript,
or making unrelated repository changes.
